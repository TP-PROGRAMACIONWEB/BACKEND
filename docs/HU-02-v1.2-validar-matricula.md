## 1. Timeout real (CA03)

El caso de prueba pide la notificación "al superar 1 minuto sin respuesta". Antes
eso no se podía cumplir, porque no había ninguna espera.

- La consulta al padrón tiene un límite de tiempo: `MATRICULA_TIMEOUT_SEGUNDOS`,
  **60 por defecto**. Si no responde dentro de ese tiempo, el resultado es
  `Timeout`.
- Aplica a **toda** validación, no solo a la matrícula trampa.
- La respuesta no es un error HTTP: es un `200` con `resultado: "Timeout"` y el
  mensaje del CA03. El intento queda en el historial y la notificación en la
  campana, igual que cualquier otro resultado. Se puede reintentar enseguida.
- La **matrícula trampa** ya no responde al instante: simula un padrón que no
  responde, así que devuelve `Timeout` recién al cumplirse el límite.

| Tipo de profesional | Matrícula trampa |
| ------------------- | ---------------- |
| Gasista             | `9999999999`     |
| Aire acondicionado  | `99999999`       |

Se sigue apagando con `MATRICULA_TRAP_HABILITADA=false`; apagada, esos números
dan `No_Encontrada`.

**Qué no cubre el límite:**

- La base caída: falla rápido con error (500), porque tampoco se puede guardar
  el intento.
- Un request que nunca llega al backend (sin red, Vercel caído). Ese caso lo
  tiene que cubrir el **frontend**, con su propio timeout de 60 segundos y el
  mismo mensaje.

**Para el frontend:** el request de validación puede tardar hasta 60 segundos;
no hay que cortarlo antes.

## 2. Campo `fidelizado` (CA08)

- Columna nueva `USUARIO.fidelizado`, booleana, **0 por defecto**.
- Pasa a 1 cuando el usuario fideliza su primera matrícula (resultado
  `Validada`). Ningún otro resultado la modifica.
- Se devuelve en `GET /api/v1/auth/me` y en el listado de usuarios del
  Administrador.
- La **tabla intermedia** que pide el caso es `MATRICULA`, que ya existía:
  `oferente_id` es el mismo `id_usuario` (clave compartida), más el tipo y el
  número. Solo se escribe con `Validada`; un intento fallido no deja fila ahí
  (queda en `VALIDACION_MATRICULA`, el historial).
- Los estados se guardan como texto (`Validada`, `No_Encontrada`, `Timeout`,
  `Ya_Fidelizada`, `Reemplazo_Solicitado`, `Vencida`, `Nombre_No_Coincide`).

Migración: `a3f1c9d27b54`. Agrega la columna y la pone en 1 para los usuarios
que ya tenían una matrícula fidelizada.

## 3. Tipos de profesional y dígitos (CA01)

`GET /api/v1/oferentes/me/matriculas/tipos` (requiere sesión) devuelve los tipos
en orden alfabético, con la cantidad de dígitos de cada uno:

```json
[
  { "tipo_profesional": "Aire acondicionado", "digitos": 8 },
  { "tipo_profesional": "Gasista", "digitos": 10 }
]
```

Sirve para armar el selector (la primera opción es la que viene por defecto),
el placeholder y el label "\*Debe ingresar X dígitos". Si se manda un número con
otra cantidad de dígitos, el backend responde `422` con ese mismo texto.

## Despliegue

1. **Migrar antes de desplegar.** Correr `migrar_bd.bat` contra Supabase
   **antes** del push a `main`. Si se despliega primero, todos los endpoints con
   login fallan con 500 hasta que se migre.
2. **Duración máxima de la función en Vercel.** Si es menor a 60 segundos,
   Vercel corta el request con 504 antes de que el backend responda `Timeout`.
   Hay que subir ese máximo, o bajar `MATRICULA_TIMEOUT_SEGUNDOS` en las
   variables de entorno de producción.
3. Cargar `MATRICULA_TIMEOUT_SEGUNDOS` en Vercel si se quiere un valor distinto
   de 60.
